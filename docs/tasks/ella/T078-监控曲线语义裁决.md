## 一、背景与问题

### 1.1 现状梳理

T072 落地后，`realtime` 接口 `maxPressure` 字段采用 **"今日峰值"** 语义（从 Redis `stat:today` 读取当日累计最大压力值），TestIT 断言已通过并 merge。但 admin-web 监控页"实时压力曲线"误将该字段当作 **"逐帧瞬时值"** 使用——每帧轮询时将 `maxPressure` push 到历史序列绘图，导致画出来是一条**不动的横线**（当日峰值在多帧内恒定），曲线失真。

这是 **"同一个字段、两个页面要两种语义"** 的契约冲突：
- **Dashboard 页**：需要 `"今日峰值"` 显示在统计卡片（当前语义正确）
- **Monitor 页**："实时压力曲线"需要 `"逐帧瞬时最大值"`（当前语义错误）

### 1.2 代码位置定位

#### 后端：data-service (`services/data-service/internal/service/record.go`)

```go
// GetRealtimeFromDB (L406-470) —— 返回 model.RealtimeSnapshot
func (s *RecordService) getRealtimeFromDB(ctx context.Context, patientID string) (*model.RealtimeSnapshot, error) {
    // ... 构建 PressureRecords（最新帧）...
    
    // 今日统计（stat:today）(L437-451)
    stats, err := s.cache.GetStatToday(ctx, patientID)
    if err != nil {
        return nil, model.ErrInternal("read stat:today: %v", err)
    }
    if v, convErr := strconv.Atoi(stats["wear_minutes"]); convErr == nil {
        snapshot.TodayHours = float64(v) / 60.0
    }
    if v, convErr := strconv.ParseFloat(stats["max_pressure"], 64); convErr == nil {
        snapshot.MaxPressure = v  // 🔴 此处：今日累计最大（非逐帧瞬时）
    }
    snapshot.MaxPoint = stats["max_point"]
    // ...
}
```

**关键事实**：
- `MaxPressure` 从 Redis Key `stat:today:{patient_id}` 读取（`max_pressure` 字段）
- `stat:today` 在设备上报时更新（`applyRealtimeCache` L165-173），逻辑为**当日累计最大**
- TestIT 断言当前语义（`services/data-service/internal/service/record_test.go L867`）：
  ```go
  assert.InDelta(t, 25.5, snap.MaxPressure, 0.1) // 今日峰值固定 25.5
  ```

#### 前端：admin-web (`apps/admin-web/src/pages/monitor/index.vue`)

```javascript
// refreshTick (L305-327) —— 每 3 秒轮询 realtime 接口
async function refreshTick() {
    const snap = await fetchPatientRealtime(pid)
    snapshot.value = snap
    // 曲线：优先 maxPressure 字段（对齐接口）(L309-314)
    let curV = snap.maxPressure ?? 0
    if (!curV || curV <= 0) {
      const hm = snap.pressureHeatmap ?? []
      curV = hm.reduce((m, p) => (p.pressureValue > m ? p.pressureValue : m), 0)
    }
    if (pressureHistory.value.length === 0) {
      initHistory(curV)
    } else {
      pushHistory(curV)  // 🔴 问题点：将 今日峰值 作为逐帧值 push 到曲线
    }
    // ...
}
```

**关键事实**：
- `pressureHistory` 用 Chart.js 绘制"实时压力曲线"，期望值是**逐帧变化**的压力数据
- 实际 `snap.maxPressure` 多帧恒定 → 曲线显示为**横线**（失真）

Dashboard 顶栏卡片正确展示 `"今日峰值"`，无需变化：
```vue

  {{ snapshot.maxPressure }} N
```

## 二、方案对比

### 方案 A：保持后端语义不变，前端曲线改画逐帧 Max

#### 改动描述
- **后端（Iris）**：`realtime` 接口 `maxPressure` **保持 "今日峰值" 语义**不动（`stat:today` 读取）
- **前端（Iris）**：
  1. **顶部 "今日峰值"**：独立展示 `snap.maxPressure`（与 Dashboard 一致）
  2. **"实时压力曲线"**：改用 **points 数组的逐帧最大值**（从 `snapshot.pressureRecords[0].points` 计算）
     - 若后端未暴露逐帧 points（假设只返回统计摘要），则需后端补字段 `latestFrameMax`（最新帧的最大压力值）

#### 影响面分析

| 层面 | 改动文件 | 改动内容 | 风险 |
|---|---|---|---|
| 前端（主改动） | `apps/admin-web/src/pages/monitor/index.vue` | 曲线数据来源改从 `pressureRecords[0].points` 计算最大值；顶栏新增 "今日峰值" 卡片 | 低（纯前端交互调整） |
| 后端（可能需补字段） | `services/data-service/internal/service/record.go` + `internal/model/model.go` | 若前端无法拿到逐帧 points，新增 `latestFrameMax` 字段返回至 `RealtimeSnapshot` | 中（需改 DTO + 测试适配） |
| 测试 | `e2e/tests/admin-monitor.spec.ts` | Monitor 页 E2E 断言需改为验证曲线有波动（非横线）+ 今日峰值独立显示 | 低（断言逻辑调整） |
| 契约 | TestIT | ❌ **无需改动**（`maxPressure` 语义保持 "今日峰值"） | ✅ 最低风险 |

#### 优点
1. **测试契约稳定**：TestIT 断言不用改，维持 T072 验收成果
2. **改动面小**：前端主导，后端仅可能补一个轻量字段（`latestFrameMax`）
3. **硬件联调口径一致**：小顾正在测 `realtime`，不改语义避免重新对齐

#### 缺点
1. **前端计算负担**：每帧需从 20 点 points 遍历找 Max（性能可忽略，但代码复杂度略增）
2. **若后端不补字段**：前端拿不到 points（假设 realtime 只返回统计摘要），需倒逼后端改 DTO

### 方案 B：realtime 回归 "最新帧" 语义，TestIT 断言同步改

#### 改动描述
- **后端（Winner）**：`realtime` 接口 `maxPressure` 改为 **"最新帧瞬时最大值"**（从最新上传帧的 `points` 计算，而非 `stat:today`）
- **后端（新增端点/字段）**："今日峰值"另出独立字段 `todayMaxPressure`（仍从 `stat:today` 读）或新端点 `/api/v1/admin/records/today-stats`
- **测试（Ella）**：TestIT 断言全部改签为 "最新帧语义"（原 `stat:today` 断言失效）
- **前端（Iris）**：Monitor 曲线继续使用 `maxPressure`（语义变回逐帧），Dashboard 改取 `todayMaxPressure`

#### 影响面分析

| 层面 | 改动文件 | 改动内容 | 风险 |
|---|---|---|---|
| 后端（主改动） | `services/data-service/internal/service/record.go` | `getRealtimeFromDB` 中 `MaxPressure` 改从最新帧计算；新增 `TodayMaxPressure` 字段 | 中（业务逻辑变更 + DTO 扩展） |
| 测试 | `services/data-service/internal/service/record_test.go` + TestIT | 所有 `maxPressure` 相关断言改为预期最新帧值（非今日固定值） | 高（契约重写 + 回归测试） |
| 前端 | `apps/admin-web/src/pages/monitor/index.vue` + `dashboard/index.vue` | Monitor 无感（继续用 `maxPressure`）；Dashboard 改取 `todayMaxPressure` | 低（字段名调整） |
| 其他服务 | alert-service（若依赖 realtime） | 需验证是否受 `maxPressure` 语义变更影响 | 未知（依赖探查） |

#### 优点
1. **语义统一**：`maxPressure` 名称与 "最新帧 Max" 直观对应（更符合 "realtime" 直觉）
2. **前端简单**：Monitor 曲线直接使用接口字段，无需额外计算

#### 缺点
1. **测试契约破坏**：TestIT 全量改签，T072 验收成果需推倒重来（违反"测试契约稳定性"原则）
2. **改动面大**：后端核心逻辑 + 测试 + 可能的依赖服务联动（回归风险高）
3. **硬件联调中断**：小顾正在测 `realtime`，语义突变需重新对齐（延迟联调进度）

## 三、推荐方案与理由

### 推荐：**方案 A**（保持后端语义不变，前端曲线改画逐帧 Max）

### 核心理由（三条）

#### 1. **测试契约稳定性：方案 A 零破坏，方案 B 全量重写**
   - T072 刚落地，TestIT 通过验证了 `maxPressure` = `stat:today` 的契约（当日累计峰值符合业务定义：用户关心 "今天压到多少" 而非 "上一帧压到多少"）
   - 方案 B 需重写所有相关断言（`record_test.go` + E2E），浪费已有验收成果；方案 A 仅需前端调整，TestIT 完全不用动
   - **原则**：测试契约一旦通过验收，应尽量避免反向修改（除非发现需求理解根本错误）

#### 2. **改动面与风险：方案 A 前端主导，方案 B 后端牵一发而动全身**
   - 方案 A 主改动在 frontend（Vue 组件 + 可能补一个轻量 DTO 字段），后端 `stat:today` 逻辑完全不动
   - 方案 B 涉及后端 `getRealtimeFromDB` 核心逻辑重写的、DTO 扩展现有字段语义、测试全量回归、潜在依赖服务影响（如 alert-service 可能依赖 `maxPressure` 做告警判定）
   - **数据**：方案 A 预估改动 < 5 文件（前端 2-3 个 + 后端 DTO 1-2 个）；方案 B 预估改动 ≥ 10 文件（后端 service + model + test + 前端 + 其他服务探查）

#### 3. **硬件联调口径：方案 A 不影响小顾当前测试，方案 B 需重新对齐**
   - 小顾正在基于当前 `realtime` 接口做硬件联调（设备上报 → realtime 查询验证），语义突变更换会导致联调数据混乱
   - 方案 A 保持 `maxPressure` 语义不变，小顾测试口径无需调整；方案 B 需通知小顾暂停联调，等接口重构后再重新对齐
   - **时间成本**：方案 B 至少延迟 1-2 天联调进度（回归测试 + 重新解释接口）

### 方案 A 实施前提

- **最优路径**：`realtime` 接口已返回 `pressureRecords` 数组（包含最新帧的 20 点 points），前端可从 `points` 遍历计算逐帧 Max
- **降级路径**：若 `realtime` 当前只返回统计摘要（不含 latest frame），则后端需补字段 `latestFrameMax`（`float64`，从 RT 缓存 `rt:frame:{device_id}` 读取最新帧计算）
